## SoleMate — 사전 부검 분석

> **Pre-mortem이란?**  
> 프로젝트가 실패했다고 가정하고 역방향으로 원인을 분석하는 기법 (Gary Klein, 1998)

## 1. 가상 실패 선언

> *2026년 7월. SoleMate은 서비스를 종료했다.  
> 사용자는 모이지 않았고, 추천은 신뢰받지 못했으며, 팀은 지쳐 흩어졌다.  
> 무엇이 잘못되었는가?*

## 2. 실패 시나리오 분석

### 🔴 Category A — 데이터 리스크

---

**A1. 리뷰 데이터의 품질이 기대보다 훨씬 낮았다**

| 항목 | 내용 |
|------|------|
| 실패 시나리오 | 무신사·네이버 리뷰의 70%가 "좋아요", "빠른 배송" 수준의 저품질 후기. 발 타입·착용감 관련 유의미한 데이터를 추출할 수 없었다 |
| 실패 확률 | ⭐⭐⭐⭐ 높음 |
| 사전 대응 | MVP 단계에서 크롤링 전 샘플 데이터 품질 검증 필수. 유튜브 영상 자막·댓글에서 전문 리뷰어 데이터 우선 확보. 커뮤니티(러닝 카페, 마라톤 포럼) 데이터 소스 다변화 |

---

**A2. 브랜드 스펙 데이터가 표준화되어 있지 않았다**

| 항목 | 내용 |
|------|------|
| 실패 시나리오 | 나이키는 스택 높이를 공개하지 않고, 아식스와 미즈노는 라스트 폭 기준이 달라 브랜드 간 비교가 불가능했다 |
| 실패 확률 | ⭐⭐⭐ 보통 |
| 사전 대응 | 브랜드 공식 스펙 + 전문 리뷰 매체(Runner's World, 런플래닛 등) 보조 데이터 활용. 스펙 미공개 모델은 커뮤니티 측정값 수집 |

---

**A3. 데이터가 특정 브랜드·모델에 편중되었다**

| 항목 | 내용 |
|------|------|
| 실패 시나리오 | 나이키·아디다스 리뷰는 수만 건이지만 브룩스·써코니·미즈노는 리뷰 수가 너무 적어 추천 신뢰도가 낮았다 |
| 실패 확률 | ⭐⭐⭐⭐ 높음 |
| 사전 대응 | 리뷰 수 가중치 조정. 리뷰 적은 브랜드는 전문가 평가 데이터(매체 리뷰)로 보완. 데이터 불충분 시 추천에서 "데이터 부족" 명시 |

---

### 🟠 Category B — 추천 엔진 리스크

---

**B1. AI 추천이 뻔하고 차별화되지 않았다**

| 항목 | 내용 |
|------|------|
| 실패 시나리오 | 어떤 조건을 입력해도 결과가 나이키 베이퍼플라이, 아디다스 아디제로, 아식스 카야노 3개로 수렴. "그냥 네이버 검색이랑 똑같네"라는 반응 |
| 실패 확률 | ⭐⭐⭐⭐ 높음 |
| 사전 대응 | 추천 결과 다양성 보장 로직 추가. 동일 결과 반복 시 프롬프트 재설계. 예산·브랜드 우선순위 필터를 강하게 적용해 결과 분산 유도 |

---

**B2. Claude API 프롬프트 설계가 부실해 추천 이유가 허술했다**

| 항목 | 내용 |
|------|------|
| 실패 시나리오 | "이 러닝화가 좋습니다"만 반복하고, 내전·코스·예산을 고려한 구체적 근거 없이 일반적인 설명만 출력 |
| 실패 확률 | ⭐⭐⭐ 보통 |
| 사전 대응 | 프롬프트에 사용자 입력값 전체를 구조화해서 전달. "왜 이 신발인가"를 반드시 포함하도록 출력 형식 고정. 프롬프트 반복 테스트 필수 |

---

**B3. 발 타입 자가진단의 오류율이 높았다**

| 항목 | 내용 |
|------|------|
| 실패 시나리오 | 사용자가 자신의 내전·외전 여부를 모르거나 잘못 입력. 잘못된 입력 → 잘못된 추천 → "앱이 이상하다"는 불신 |
| 실패 확률 | ⭐⭐⭐⭐ 높음 |
| 사전 대응 | 발 타입 자가진단 가이드 화면 추가 (젖은 발자국 테스트 이미지 등). 불확실한 경우 "중립으로 추천 후 전문가 확인 권장" 안내. 신발 밑창 닳은 패턴으로 추정하는 보조 가이드 제공 |

---

### 🟡 Category C — 사용자 경험 리스크

---

**C1. 입력 항목이 너무 많아 이탈률이 높았다**

| 항목 | 내용 |
|------|------|
| 실패 시나리오 | "발 모양이 이집트형인지 그리스형인지 어떻게 알아요?" 입력 도중 포기. 완료율 20% 미만 |
| 실패 확률 | ⭐⭐⭐⭐⭐ 매우 높음 |
| 사전 대응 | 필수 입력 최소화 (성별·예산·기록·러닝 목적 4개만으로 기본 추천). 선택 입력은 "더 정확한 추천을 위해" 옵션으로 분리. 각 항목에 시각적 가이드 이미지 제공 |

---

**C2. "데이터 기반"이라는 신뢰가 형성되지 않았다**

| 항목 | 내용 |
|------|------|
| 실패 시나리오 | "결국 이것도 광고 아니야?" 의심. 추천 근거가 불투명해 SNS 추천글과 차별화가 없다는 인식 |
| 실패 확률 | ⭐⭐⭐ 보통 |
| 사전 대응 | 추천 결과 화면에 분석 근거 수치 공개 ("무신사 리뷰 2,847건 분석 기반"). 브랜드 제휴 없음 명시. 리뷰 출처 투명하게 표시 |

---

**C3. 모바일 UX가 불편했다**

| 항목 | 내용 |
|------|------|
| 실패 시나리오 | 러닝 관련 검색은 대부분 스마트폰으로 이루어지는데, PC 기준으로 설계된 폼이 모바일에서 사용하기 불편했다 |
| 실패 확률 | ⭐⭐⭐ 보통 |
| 사전 대응 | 모바일 퍼스트 설계. Tailwind CSS 반응형 컴포넌트 우선 적용. 터치 친화적 카드 선택 UI 사용 |

---

### 🟢 Category D — 팀 & 실행 리스크

---

**D1. 해커톤 당일 Claude API 연동에서 막혔다**

| 항목 | 내용 |
|------|------|
| 실패 시나리오 | API 키 설정, CORS 오류, 응답 파싱 문제로 데모 당일 핵심 기능이 작동하지 않음 |
| 실패 확률 | ⭐⭐⭐⭐ 높음 |
| 사전 대응 | 해커톤 전날 API 연동 테스트 완료 필수. Fallback으로 하드코딩된 샘플 응답 준비. 인터넷 연결 불안정 대비 오프라인 데모 버전 별도 준비 |

---

**D2. 역할 분담이 불명확해 중복·공백이 생겼다**

| 항목 | 내용 |
|------|------|
| 실패 시나리오 | 4명이 각자 다른 부분을 만들었는데 합치는 과정에서 충돌. 누가 Claude 프롬프트를 담당하는지 몰라 마지막에 급조 |
| 실패 확률 | ⭐⭐⭐ 보통 |
| 사전 대응 | 역할 명확화: UI(이커머스), API 연동(통신), 추천 로직(보험), 데이터/DB(정유). 매일 15분 싱크업 필수. 공유 GitHub 레포 + 브랜치 전략 사전 합의 |

---

**D3. 발표 스토리와 데모가 따로 놀았다**

| 항목 | 내용 |
|------|------|
| 실패 시나리오 | 발표는 "부상 예방"을 말하는데 데모는 단순 필터 검색처럼 보임. 심사위원이 차별화 포인트를 이해하지 못함 |
| 실패 확률 | ⭐⭐⭐ 보통 |
| 사전 대응 | 데모 시나리오 사전 픽스: "서울마라톤 출전 예정, 내전, 예산 15만" 시나리오로 고정. 발표 내러티브와 데모 흐름을 하나의 스크립트로 통합 연습 |

## 5. Pre-mortem 핵심 교훈

> **가장 위험한 실패는 "만들었는데 아무도 안 쓰는 것"이 아니라**  
> **"써봤는데 믿을 수 없는 것"이다**

RunFit의 핵심 차별화는 **신뢰**다.  
데이터 기반이라는 포지셔닝을 끝까지 지키기 위해  
추천 근거의 투명성, 입력 가이드의 정확성, API 연동의 안정성을  
타협 없이 챙겨야 한다.
